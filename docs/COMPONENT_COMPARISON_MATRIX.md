# TimeTrack — Component Comparison Matrix

**Prepared by:** Senior Technical Architect review (Cline-assisted)
**Date:** 2026-09-16 (rev 2 — post v1.4.0 feature batch + OpenAPI drift closure)
**System:** Multi-tenant workforce management platform — React 19 SPA + Expo
WebView shell → Express 5 API → PostgreSQL/Prisma, Redis-optional,
Railway-hosted, live in production (Play Store releases through vc17).

**Evidence base:** code inspection, `docs/AUDIT_REGISTER.md` (living
register), CI workflows, migration ledger (`docs/DATA_CHANGES.md` 001–013),
and live gate runs at time of writing: typecheck (web+server) clean,
49 suites / 467 unit tests passing, production build passing,
`server/docs/openapi.json` regenerated and drift-guarded.

> Scores are engineering judgments anchored to mechanical evidence (gate
> results, LOC measurements, register state) — not marketing numbers.

## 2. Interdependency Analysis

| Component → depends on | Frontend                                  | Backend                                                  | Database                                                       | API Contracts                                        | Arch. Patterns                                        |
| ---------------------- | ----------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------- |
| **Frontend**           | —                                         | **Critical** (every screen; typed client mirrors routes) | Low (never direct)                                             | **High** (client types + spec shape UI expectations) | High (hybrid shell assumes web-first punch path)      |
| **Backend**            | Low (serves build; SSE consumers)         | —                                                        | **Critical** (Prisma client generated from schema; RLS bridge) | **Critical** (Zod schemas _are_ the contract)        | **Critical** (ALS tenant context gates every request) |
| **Database**           | None                                      | High (RLS policies assume backend sets tenant context)   | —                                                              | Medium (enum/field renames ripple into spec)         | High (multi-tenancy realized in RLS + indexes)        |
| **API Contracts**      | Medium (consumed types)                   | **Critical** (generated from backend Zod)                | Medium (schema shapes responses)                               | —                                                    | Medium (ADR-0004 fixes transport contract)            |
| **Arch. Patterns**     | High (shell/WebView bridge, punch dedupe) | **Critical** (layering, DI, locks)                       | High (tenant bridge, migration-guard philosophy)               | High (versioning policy)                             | —                                                     |

**Reading:** the Database→Backend→Contracts spine is the system's **critical
path** — a schema change propagates through generated client, Zod, OpenAPI and
UI types in one hop each. The Frontend is the most _replaceable_ layer
(WebView shell + SPA); Architectural Patterns are the most _load-bearing_
(removing the ALS/RLS bridge would silently break tenant isolation).

| Pair                          | Verdict                                                      | Key contrasts                                                                                                                                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Frontend vs Backend**       | Backend wins on discipline; Frontend wins on UX completeness | Backend: fail-closed errors, DI-tested logic, fail-fast config. Frontend: richer feature surface but 6 files >950 LOC, `any` casts, thinner per-component coverage. Both share the same lint/format gates — the difference is _module hygiene_, not tooling    |
| **Backend vs Database**       | Database is the strongest component                          | DB has guard-aborting migrations, a written ledger with rollback paths per entry, RLS FORCED, restore drills. | **API Contracts vs Frontend** | Contracts more rigorous, Frontend more exposed               | Contracts benefit from Zod↔OpenAPI single-source generation, now enforced by a fail-closed predeploy guard (rev 2); the Frontend consumes them through a hand-maintained 1014-LOC client — the duplication point where drift would surface first               |
| **Arch. Patterns vs Backend** | Patterns better _documented_, Backend better _tested_        | ADRs + register give patterns traceability; but the patterns' flagship risk (auto-clock triplication) spans web/native/server, and only the server slice is DI-unit-tested. | **Database vs API Contracts** | DB wins on change safety                                     | Every DB change has a ledger entry + rollback path + preflight; contract changes have a changelog and — as of rev 2 — a regeneration guard in `predeploy-check.mjs` step 4/4 (previously manual discipline only)                                               |

## 5. Overall Confidence Correlation

| Component      | Confidence | Primary constraint                          | Secondary constraint               | Mitigation status                                                 |
| -------------- | ---------- | ------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------- |
| Frontend       | **92%**    | Module size (6 files >950 LOC)              | `any` casts; coverage depth        | ⏳ Ratchet armed (warn); splits open (Open-09)                    |
| Backend        | **94%**    | Route-module size (4 files >900 LOC)        | Auto-clock duplication server-side | ⏳ Extraction planned (Open-08); DI pattern proven                |
| Database       | **94%**    | Owner-gated clone RLS re-provision          | `salaryInfo Json?` untyped         | ✅ Guards/ledger/drills closed; re-provision order documented     |
| API Contracts  | **94%**    | ~~Spec regeneration not enforced~~          | No consumer-driven contract tests  | ✅ **Drift guard shipped (rev 2)**; contract tests remain open    |
| Arch. Patterns | **91%**    | Auto-clock triplication (web/native/server) | Native slice untyped (`App.js`)    | ⏳ Phase-3 consolidation tracked; server slice extracted & tested |

**Correlation insight:** confidence tracks _enforcement mechanism maturity_,
not effort. Components with **mechanical fail-closed gates** (Database: guard
migrations + preflight; Backend: fail-fast config + CI) score highest.
Components relying on **warn-level or manual discipline** (Frontend
`max-lines`) score lowest — every point below 94% maps to a gate that warns
instead of fails. Rev 2 applied that lesson directly: the API-contract gap
was closed not by regenerating the spec once, but by converting the
regeneration check into a hard deploy gate. The next highest-leverage moves
are the same conversion for `max-lines` (new files → error) and per-area
coverage ratchets.
